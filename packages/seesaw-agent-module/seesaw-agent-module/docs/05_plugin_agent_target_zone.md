# 5. ChatGPT / Agent Plugin Target Zone

## 5.1 Plugins are adapters

Seesaw treats agent plugins as **distribution adapters**, not companies.

Bad thesis:

```text
we win because we have a ChatGPT plugin
```

Strong thesis:

```text
we own scarce state/action/supply
and ChatGPT is one distribution path into it
```

## 5.2 Ideal agent-native business

```text
User/agent intent
      |
      v
frontier cognition
      |
      v
OUR CAPABILITY
      |
      +-- reads state nobody else cheaply has
      +-- performs action model cannot do itself
      +-- records outcome
      |
      v
proprietary trajectory
      |
      v
better capability / data / economics
```

## 5.3 Plugin suitability filter

A capability is especially plugin-native when it requires:

- current state;
- exact lookup;
- authenticated state;
- write authority;
- transaction;
- booking;
- communication;
- physical action;
- verification;
- scarce data.

A capability is weak when it is only:

- reasoning;
- writing;
- generic research;
- generic summarization;
- generic code generation.

## 5.4 Lab-attack resistant plugin portfolio

Prefer plugins whose backend owns:

```text
identity
permissions
live data
economic supply
marketplace liquidity
outcomes
physical state
trust
```

The model can improve indefinitely without replacing these.

## 5.5 Project implication

The correct development order is:

```text
1. Identify scarce backend state/action.
2. Build/own that kernel.
3. Reuse commodity implementation around it.
4. Expose via ChatGPT/MCP/API.
5. Capture outcomes.
6. Feed outcomes back into Seesaw.
```

Never invert this and start from "what plugin should we make?" unless the answer reveals a scarce backend asset worth owning.
